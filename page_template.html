The patterns

  1. Access, not protocol, is the bottleneck. %%mcp_official%% of 100 apps now have an official vendor MCP server, and %%rest%% have a documented REST or GraphQL API. What separates "ready" from "not" is how a developer gets credentials: %%free%% free self-serve, %%trial%% trial-only, %%paid%% paid plan, %%approval%% vendor approval, %%partner%% partner/sales gate, %%noapi%% with no public API.
  2. Static keys are the default; OAuth2 is common but rarely the only option. %%static%% apps accept a static credential (API key, personal token, Basic), %%oauth%% support OAuth2, and %%both%% support both. Only %%oauth_only%% are OAuth2-only, so a toolkit must own a registered OAuth app: %%oauth_only_list%%.
  3. Self-serve depends on the category. Productivity (%%prod_free%%/10) and developer platforms (%%dev_free%%/10) are almost entirely free self-serve. Helpdesks are the opposite: %%support_paid%%/10 need a trial or paid plan before the API works, so test accounts expire and the toolkit costs money to keep tested.
  4. Besides paying, the most common gate is vendor app review, and it sits in ads and social. %%approval%% apps issue credentials but need review or production approval before real use: %%approval_list%%. %%mkt_approval%% of the 10 marketing apps are in this group. That is process work, not partnerships.
  5. Hard walls are rare. Only %%partner%% apps sit behind a sales or partner gate (%%partner_list%%), plus %%noapi%% with no API at all. Those are the outreach list.
  6. Composio already covers %%composio%% of the 100. The gaps are not the hard apps: %%missing_buildable%% of the %%missing%% apps without a toolkit are buildable today (next section). That list is the cheapest place to add coverage.

Verification: how accurate is this, and how do we know?

Before any agent output existed, I drew a seeded, stratified sample (2 apps per category, sample.py) and built an answer key for it in a separate interactive session. Reviewer agents collected verbatim quotes from vendor pages without access to the pipeline output. Labels were decided from those quotes, and pages that hide facts from fetchers were checked in a real browser: Devin's pricing table uses icons, Otter's help center returns 403 to bots. Where docs are genuinely ambiguous, the key lists every acceptable answer. The key was hashed and frozen before scoring (truth/FROZEN.txt). Each app is scored on 5 fields: auth, access, API, MCP and verdict, %%nfield%% field checks in all.

%%acc%%

Scored against the frozen key, untouched since it was hashed. After the two documented corrections below, the same stages score %%ap1%% → %%aver%% → %%afin%%%. With %%nfield%% field checks, a 95% Wilson interval on the final score is %%ci_lo%%–%%ci_hi%%%. Fields within one app are correlated, so the true uncertainty is wider.

What each loop caught

  • Verifier agent (pass 2) re-fetched every cited page and checked %%nchecks%% claims: %%supported%% supported, %%contradicted%% contradicted, %%unsupported%% unsupported. It changed at least one field on %%changed_apps%% apps. Example: pass 1 called Meta's Marketing API "GraphQL" because it is named the Graph API, but it is REST.
  • Rule verdict. Left to itself, the model hedged: it labelled %%llm_caveats%%/100 apps "ready with caveats", which makes the column useless. The verdict is now computed from the verified access and API fields, using the definition already in the research prompt (score.py: rule_verdict). I added this after seeing pass 1, and the table shows it as its own row.
  • A gate that failed. My first fix for unverifiable records blocked every app where the verifier could confirm neither access nor API. It fired on 7 apps, and 6 were false positives (Salesforce, Airtable, Gumroad and others). "Unsupported" mostly meant the docs were JavaScript-rendered and did not load. I removed it.
  • Recheck agent (pass 3) replaced that gate. It runs only on those flagged apps (%%recheck_list%%) and is told to reach the vendor's own docs by other routes: llms.txt, .md versions of pages, the vendor's GitHub, its help center. It kept the existing access answer on all 8, so it changed no scored field. Its value was evidence: it found fanbasis's docs on a separate domain that my answer key had missed. The 93 → 96 step on the sample comes entirely from the rule verdict.

The agent: what it does and where it needed a human

1 · ResearchOne headless Claude Code session per app (claude -p, Sonnet), only WebSearch + WebFetch, output forced into schema.json. 6 in parallel; resumable.
2 · VerifyA fresh session per app gets the record, re-fetches each evidence URL and returns per-claim status plus a corrected record.
3 · RecheckOnly for apps whose access and API could not be confirmed: find the vendor's own docs by alternate routes.
4 · RulesVerdict computed from verified fields. Composio coverage joined from the catalog.
5 · ScoreCompare against the hand-built, frozen answer key on the 20-app sample (score.py).
6 · Publishbuild_page.py renders this page and data.json from the outputs; no hand-typed numbers.

Where a human was needed

  • Defining the output contract: access tiers, the verdict rule, and what counts as evidence.
  • Building and adjudicating the answer key, including browser checks of pages that hide facts from fetchers.
  • Noticing the model's hedged verdicts and the gate's false positives. Neither failure shows up without an answer key.
  • Matching apps to Composio toolkits. Some slugs are ambiguous (marked * in the table): amazon may not be SP-API, and youtube_transcript may not be transcriptapi.com.
  • Operations: the Claude Code auto-updater removed the binary mid-run (43 failed calls) and a usage cap stopped one batch. Resumable runs plus a retry made both a rerun, not a restart.

Run it

Needs Python 3.10+ and Claude Code logged in. No API keys and no pip installs.

python3 agent.py research   # pass 1
python3 agent.py verify     # pass 2
python3 agent.py recheck    # pass 3 (flagged apps only)
python3 score.py            # accuracy vs answer key
python3 build_page.py       # this page + data.json

Cost for the full run: about $14 of API-equivalent usage on a Claude plan, 2–3 minutes per app per pass, 6 apps in parallel.

Limits, stated plainly

  • Accuracy was measured on 20 apps (%%nfield%% field checks), not all 100. The other 80 went through the same three agent passes but no answer-key check.
  • The answer key was built with AI help (reviewer agents gathering quotes, plus browser checks), not by reading every page unaided. It was wrong twice, and both corrections are shown above.
  • "Ready" vs "caveats" depends on a definition, and this page uses one: ready means free self-serve credentials plus a documented API. API breadth and one-line descriptions are reported but not scored.
  • Vendor terms change. The Meta Ads MCP opened in July 2026, Help Scout's MCP went GA in July 2026, and FanBasis renamed itself Commas in July 2026. This is a snapshot as of November 2026.
  • fanbasis: the final record still says its MCP is community-built. The vendor publishes an official one.

Machine-readable: data.json holds all 100 final records, including per-claim verifier status and evidence URLs. Answer key: truth/labels.json and truth/adjudications.json in the repo.
