The patterns

  1. Access, not protocol, is the bottleneck. 82 of 100 apps now have an official vendor MCP server, and 98 have a documented REST or GraphQL API. What separates "ready" from "not" is how a developer gets credentials: 50 free self-serve, 15 trial-only, 19 paid plan, 10 vendor approval, 5 partner/sales gate, 1 with no public API.
  2. Static keys are the default; OAuth2 is common but rarely the only option. 87 apps accept a static credential (API key, personal token, Basic), 74 support OAuth2, and 63 support both. Only 11 are OAuth2-only, so a toolkit must own a registered OAuth app: Podio, Zoho CRM, Zoho Cliq, LinkedIn Ads, Threads (Meta), Salesforce Commerce Cloud, Amazon Selling Partner, QuickBooks, Xero, Ramp, NotebookLM.
  3. Self-serve depends on the category. Productivity (9/10) and developer platforms (7/10) are almost entirely free self-serve. Helpdesks are the opposite: 9/10 need a trial or paid plan before the API works, so test accounts expire and the toolkit costs money to keep tested.
  4. Besides paying, the most common gate is vendor app review, and it sits in ads and social. 10 apps issue credentials but need review or production approval before real use: Lark (Larksuite), WhatsApp Business, Google Ads, Meta Ads, LinkedIn Ads, Pinterest, Threads (Meta), Amazon Selling Partner, Plaid, QuickBooks. 5 of the 10 marketing apps are in this group. That is process work, not partnerships.
  5. Hard walls are rare. Only 5 apps sit behind a sales or partner gate (DealCloud, Salesforce Commerce Cloud, Waterfall.io, Paygent Connect, PitchBook), plus 1 with no API at all. Those are the outreach list.
  6. Composio already covers 81 of the 100. The gaps are not the hard apps: 14 of the 19 apps without a toolkit are buildable today (next section). That list is the cheapest place to add coverage.

Verification: how accurate is this, and how do we know?

Before any agent output existed, I drew a seeded, stratified sample (2 apps per category, sample.py) and built an answer key for it in a separate interactive session. Reviewer agents collected verbatim quotes from vendor pages without access to the pipeline output. Labels were decided from those quotes, and pages that hide facts from fetchers were checked in a real browser: Devin's pricing table uses icons, Otter's help center returns 403 to bots. Where docs are genuinely ambiguous, the key lists every acceptable answer. The key was hashed and frozen before scoring (truth/FROZEN.txt). Each app is scored on 5 fields: auth, access, API, MCP and verdict, 100 field checks in all.

What each loop caught

  • Verifier agent (pass 2) re-fetched every cited page and checked 500 claims: 404 supported, 29 contradicted, 67 unsupported. It changed at least one field on 33 apps. Example: pass 1 called Meta's Marketing API "GraphQL" because it is named the Graph API, but it is REST.
  • Rule verdict. Left to itself, the model hedged: it labelled 88/100 apps "ready with caveats", which makes the column useless. The verdict is now computed from the verified access and API fields, using the definition already in the research prompt (score.py: rule_verdict). I added this after seeing pass 1, and the table shows it as its own row.
  • A gate that failed. My first fix for unverifiable records blocked every app where the verifier could confirm neither access nor API. It fired on 7 apps, and 6 were false positives (Salesforce, Airtable, Gumroad and others). "Unsupported" mostly meant the docs were JavaScript-rendered and did not load. I removed it.
  • Recheck agent (pass 3) replaced that gate. It runs only on those flagged apps (Salesforce, Podio, Front, Gumroad, fanbasis, Airtable, Xero, Devin) and is told to reach the vendor's own docs by other routes: llms.txt, .md versions of pages, the vendor's GitHub, its help center. It kept the existing access answer on all 8, so it changed no scored field. Its value was evidence: it found fanbasis's docs on a separate domain that my answer key had missed. The 93 → 96 step on the sample comes entirely from the rule verdict.

The agent: what it does and where it needed a human

1 · ResearchOne headless Claude Code session per app (claude -p, Sonnet), only WebSearch + WebFetch, output forced into schema.json. 6 in parallel; resumable.
2 · VerifyA fresh session per app gets the record, re-fetches each evidence URL and returns per-claim status plus a corrected record.
3 · RecheckOnly for apps whose access and API could not be confirmed: find the vendor's own docs by alternate routes.
4 · RulesVerdict computed from verified fields. Composio coverage joined from the catalog.
5 · ScoreCompare against the hand-built, frozen answer key on the 20-app sample (score.py).
6 · Publishbuild_page.py renders this page and data.json from the outputs; no hand-typed numbers.

Where a human was needed

  • Defining the output contract: access tiers, the verdict rule, and what counts as evidence.
  • Building and adjudicating the answer key, including browser checks of pages that hide facts from fetchers.
  • Noticing the model's hedged verdicts and the gate's false positives. Neither failure shows up without an answer key.
  • Matching apps to Composio toolkits. Some slugs are ambiguous (marked * in the table): amazon may not be SP-API, and youtube_transcript may not be transcriptapi.com.
  • Operations: the Claude Code auto-updater removed the binary mid-run (43 failed calls) and a usage cap stopped one batch. Resumable runs plus a retry made both a rerun, not a restart.

Run it

Needs Python 3.10+ and Claude Code logged in. No API keys and no pip installs.

python3 agent.py research   # pass 1
python3 agent.py verify     # pass 2
python3 agent.py recheck    # pass 3 (flagged apps only)
python3 score.py            # accuracy vs answer key
python3 build_page.py       # this page + data.json

Cost for the full run: about $14 of API-equivalent usage on a Claude plan, 2–3 minutes per app per pass, 6 apps in parallel.
